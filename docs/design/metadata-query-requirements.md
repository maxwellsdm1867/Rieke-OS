# DISCO metadata query requirements

Updated 2026-10-01. Status: requirements and integration specification supported by isolated experiments; the typed query candidate is not integrated into the running app. This document updates the metadata performance design. It does not change the canonical database, dependency versions or release status.

The target workload is **one million epochs** with responsive browsing, protocol-specific selection and complete scientific metadata. Keep SQLite for the derived query index and use the measured typed/indexed read model. “Typed SQLite” means ordinary SQLite tables, typed dictionary columns, indexes and bounded SQL queries; it does not mean adopting TypeSQL or another library.

See the [session report](../dev/metadata-index-handoff-2026-10-01/README.md), [benchmark ledger](../dev/metadata-index-handoff-2026-10-01/BENCHMARKS.md) and [preserved evidence](../dev/metadata-index-handoff-2026-10-01/evidence/INDEX.md). Recorded acquisition identities and tag terminology follow [CONTEXT.md](../../CONTEXT.md).

## Architecture and required behavior

| ID | Requirement | Acceptance evidence / current status |
|---|---|---|
| MQ01 | DataJoint/native MySQL and original recordings remain authoritative. SQLite is a disposable, generation-bound read index, not a replacement scientific database. Index construction must not rewrite acquisition records or annotations. | Original source/metadata checksums, unchanged native tables, detail equivalence and rebuild/open fault checks. Source preservation passed in experiments; production integration pending. |
| MQ02 | Discover the complete eligible field catalog from imported data. Maintain protocol-specific field presence and semantics; 140 is today's observed union, not a limit or hardcoded schema. New protocol parameters become eligible on ingestion/reindex. Keep raw detail paths that are not eligible for filtering available for inspection/export. | New/changed protocol fixtures, absent fields, mixed-type fields and discovery/rebuild checks. Today's snapshot has 140 eligible query paths and 340 decoded detail paths. Future-schema tests pending. |
| MQ03 | Use stable recorded source/cell/group/block/epoch keys. Apply recorded parent relationships before scientific filtering when the scope is structurally bounded. Display labels, type classifications, identical parameters and timestamps must not establish identity. Preserve empty acquisition branches. | Scope, ancestry, identity conflicts and group ordering checks; empty-branch production integration remains open. |
| MQ04 | Preserve native predicate behavior: recorded null, absent field and not-yet-loaded detail are different states. Retain numeric/array equality, mixed-type behavior, all/any/not, validation errors and exact field paths. Do not silently equate effective epoch parameters with block settings. | Independent native-value truth, all-field fixture tests and exact result hashes. Scoped candidate passed 1,185 valid predicate cases across all 140 fields; missing/null and compound checks passed. Broader unseen scientific types remain to qualify. |
| MQ05 | Browse and tree APIs must return bounded pages with stable chronological ordering. Select narrow epoch IDs/ranks before fetching wide native row JSON. Avoid eagerly loading all epochs, constructing a million-ID Python list, or transporting that list for each action. | Exact count, row DTO, cursor and full-pagination comparison; source eligibility and generation-bound production cursors still need integration checks. |
| MQ06 | For explicit cell/block/group scopes, scientific membership should point-read the scoped epoch/field entry rather than build a project-wide posting list first. Use the measured correlated EXISTS/NOT EXISTS route where its semantics and plans are qualified. Global and broad protocol queries may need different plans. | Same-output million-row scope A/B and all-field cell/block/group fixtures. Global/protocol-only SQL unchanged. Optimize other scopes only with measurements. |
| MQ07 | Listing field definitions must not require computing distributions for every field. Request exact summaries only for active filter controls, tree axes and explicitly added fields. Keep a full-field chooser and explicit all-field summary operation. Uncommon fields remain queryable, not excluded. | Requested summaries must equal their corresponding entries in the full result; count/rows/cursor must remain equal. Four versus 140 selected-cell summaries passed. No 28-field whitelist is approved. |
| MQ08 | Separate first visible page, exact matched count, requested summaries and full catalog as measurable work. Slow global counts/aggregates must not block ordinary navigation; background/cancellable work must expose pending, stale or failed status and never substitute an unfiltered result. | End-to-end UI/HTTP traces for each completion milestone, cancellation and stale-generation faults. Design requirement; async service/UI integration pending. |
| MQ09 | Bind cache entries to metadata/source generation, scope, canonical predicate, requested fields and query policy version. Bind tag-dependent results to annotation generation and protocol/dataset/profile context. Validate generation before returning/publishing a result; bound cache memory/disk. | Source change, annotation edit, concurrent rebuild, stale cursor and restart tests. Experimental immutable checks are not complete production cache qualification. |
| MQ10 | Keep shared cell tags, inherited cell tags, shared epoch tags and protocol/dataset curation distinct. Tag changes update annotation-dependent query state without rebuilding immutable recording metadata. Preserve actors/profiles and provenance. | Existing annotation contracts plus live tag-edit/query/export/restart and dense-tag regression benchmarks. Today's real snapshot has no populated tags; synthetic tag tests do not close this gate. |
| MQ11 | Preferred summaries belong to the protocol and view, not a global fixed parameter list. Seed preferences from saved layouts, available fields and explicit scientific priorities. Preserve user-pinned fields and saved trees, including missing-field behavior; do not silently repair a saved layout. | Protocol-specific tests, newly imported protocol parameters and saved-layout restoration. Mean-noise's saved history fields are absent in this dataset; preserve that fact. |
| MQ12 | An adaptive preference layer may promote frequently used, expensive summaries to bounded caches or precomputation. Retain the complete general query path. Add specialized indexes only when a measured same-result benchmark justifies query benefit, build/storage cost and regression risk. | Usage evidence plus paired before/after measurements and invalidation checks. Proposed next phase, not implemented. Preferred 28 showed no convincing common-query gain and worse rare-field queries. |
| MQ13 | Capture explicit user query/tree actions for learning: action ID, actor/session attribution, protocol/workspace, field paths, operators, structural scope, operation kind, metadata/annotation generations, duration, outcome and count. Distinguish committed actions from preview typing, retries, refreshes and automation. Bound local retention; schema/payload logging must not expose credentials. | Replay an attributed session and verify deduplication/counts, restart/retention and overhead. Current latest-run rows and bodyless HTTP logs cannot establish usage frequency or “80% coverage.” Logging remains future work. |
| MQ14 | Full selected-epoch inspection, export and stimulus reconstruction must retain complete metadata and dependency bundles regardless of summary preference. Preserve seeds, generator/version, timing/sample rates, device/calibration context, geometry and source references. | Decoder/export equality and real recorded-vs-reconstructed stimulus checks. Metadata preservation is qualified; live H5 reconstruction is not newly qualified. |
| MQ15 | Scientific priority does not authorize inventing missing values or meanings. Pipette/amplifier offsets differ from visual centerOffset; protocol controlMode must not be relabeled clamp mode without source verification. Keep ownership, units and explicit nulls. | Acquisition/device-state source audit and field semantics tests. Electrical offsets are not identified in the cached inventory; several solution/recording fields are null/constant. |
| MQ16 | Build/rebuild derived indexes outside the active generation, verify before publication and preserve usable readers on failure. Reuse an unchanged verified generation where safe. Measure startup verification separately from steady-state query time. | Incremental rebuild, interrupted build, invalid assets, source exclusions and reader concurrency tests. Current experimental build/open receipts are baseline evidence, not shipped lifecycle behavior. |
| MQ17 | Browser development and desktop packaging use the same React/Python scientific behavior. Use the browser/dev build for rapid UI and query evaluation; package only for integration/release qualification, while retaining packaged tests. | Equivalent API/DTO and UI behavior in both runtimes. No separate HTML scientific engine or routine package rebuild per query experiment is required. |
| MQ18 | Structural navigation shortcuts must verify the supported filter policy and binding/header semantics before borrowing raw rows or reusing a scope across depths. Unsupported/custom policies retain the authoritative general reader. Group/summaries must be charged to a bounded cache before admission, including lazily allocated data. Successful refresh/publication releases obsolete row generations even when index identity is unchanged; failed validation retains the last usable generation. | The earlier 100k candidate passed custom-policy, binding, recursive allocation and weak-reference refresh tests. Preserve these guards when porting its fast path; cached Python scopes are not a substitute for million-scale SQL paging. |
| MQ19 | Complete native catalogs must batch field statistics and within-cell variation, reuse canonical stored-JSON/joint signatures on the same scoped connection, and avoid copying all IDs for an unrestricted generation. Use scope-driven joins for true subsets; retain automatic planning for full generations unless a paired measurement justifies a change. | Exact full catalog/predicate hashes, duplicate/foreign-ID order, empty scopes, joint fields and full/subset plan checks. The full-generation forced plan regressed about 5%; retain the measured plan-selection rule. |
| MQ20 | Fast validation/core-field shortcuts require a verified current-generation proof of field presence, exact native-value equality and compatible value kinds. Reuse proven kind/array-element representatives rather than decoding every recorded UUID for each query. Fields or generations without the proof use native validation/general membership. | Empty UUID lookup regression corrected from 3.78 ms to 0.076 ms on the real 2,781-row fixture; million model stores build-time representatives and proves nine core shortcuts. Retain exact validation errors and generation checks. |
| MQ21 | Metadata/index storage must remain proportional to the represented records, relationships and actual distinct values. Prefer stable references, shared ancestor/value dictionaries and one physical native base over repeated full objects or per-epoch copies of shared annotations. Bound persisted summaries, learned indexes and retained generations; avoid per-query/full-membership duplication and unbounded history. | Required real-replay storage benchmark reports total metadata, incremental index bytes, bytes/epoch, bytes/relationship, raw-recording ratios, component breakdown and rebuild high-water use. Current million metadata base is 7.196 GB plus 1.107 GB auxiliary index; this is not the metadata-to-waveform ratio. Storage regressions require a measured benefit and documented tradeoff, not just a latency win. |

## Benchmark and regression contract

| ID | Required evaluation rule |
|---|---|
| E01 | Retain all nine everyday actions: epoch selection/details, selected-metadata search, cached-cell reopening, loaded-row scrolling, unloaded-cell expansion, unloaded-block expansion, next 60 cells, tagging ten epochs and metadata-filter preview. Each must have measured or explicitly unqualified status. |
| E02 | Keep UI/HTTP timings separate from backend SQL timings. “Preview” must state whether it includes exact count, 60 rows, requested facets, full catalog, suggestions/layout and rendered completion. |
| E03 | Preserve before/after receipts, raw samples, first observation, warm median, maximum, runtime/hardware context, code/source hashes, operation/payload definition and resource caps. Collect p95/p99 only when sample counts support them; five samples do not establish tail performance. |
| E04 | Compare equal-output engine changes on the same corpus, scopes, predicates and field requests. Check independent truth, exact counts, chronology, cursors, null/missing/type/array semantics and payload hashes. Fewer requested summaries are a separately labeled workflow change. |
| E05 | Use the preserved one-million-epoch replay of actual mounted data as the required scale/regression corpus: 359 complete replicas of 2,781 epochs plus the recorded 1,621-epoch whole-block tail. Match its source/replay seals, namespace mapping, field set and oracle before comparing candidates. Smaller real fixtures may provide development checks; earlier fixed-schema synthetic results are supplemental and cannot replace this gate. Disclose repeated scientific cardinalities, source eligibility and lack of newly readable waveforms. If inputs change, establish a new paired baseline. |
| E06 | Record timeouts, memory stops, interrupted attempts and regressions as incomplete/failed measurements, not invented latencies or passes. Isolate experiments from active scientific work; avoid competing benchmark workers. |
| E07 | Measure index build time, validation/open time, added physical storage, peak memory, cold/warm behavior, pagination, tag invalidation and concurrent access. Separate reusable-core setup, corpus construction and logical storage estimates from actual costs. |
| E08 | At integration, rerun the preserved baseline and require exact semantic passes. Investigate repeatable latency/memory regressions before merging; establish numerical budgets from the integrated same-output baseline rather than claiming experimental medians as production SLOs. |
| E09 | Benchmark storage alongside speed on the required real-million replay. Record physical native metadata bytes, physical added index bytes, their total, bytes/epoch and bytes/epoch-field link, added-index/base-metadata ratio, total-metadata/raw-recording ratio, and component/index/cache/generation breakdown. State whether sizes mean file length, allocated disk, used pages or logical payload. Do not call a projected layout or shared-core experiment a physical saving. |
| E10 | Check metadata growth at the original 2,781 real records and reproducible intermediate/one-million replays, preserving field mix and replay construction. Compare per-record costs and actual bytes at equal corpus sizes; record distinct values/ancestors, fan-out, UUID encoding, slack and compression. Compare rebuild peak disk, publication overlap, bounded retention and disk after cleanup. Raw recordings reused by a replay are counted once physically; any projected million-record waveform denominator must be separately labeled and derived from recorded payloads, not invented or multiplied blindly. |

## Measured engineering direction

The complete typed SQLite candidate materially accelerates bounded metadata queries. Searching structural scope first improves selected-cell scientific queries from roughly 0.68–1.63 seconds to 2.8–5.9 ms. Requesting four selected summaries instead of all 140 reduces that selected-cell workload from 167 ms to 6.6 ms. Global two-field aggregates remain approximately 3.2 seconds.

The full selected-cell catalog is separate: the earlier native batching query preserved its complete 141-field output and reduced 25.59 seconds to 133.93 ms on the million replay. Retain its exact derived grouping/layout behavior when integrating; do not replace it with four facets and call the outputs equal.

SQLite is the current integration candidate. DuckDB remains an optional research comparator; no equivalent million-real-record DuckDB result was produced. The preferred 28 experiment is retained as rejected evidence for narrowing the index, not as the intended architecture. Broad summaries, startup verification and a complete live UI/tagging qualification remain open.

## Integration gate

Integrate the complete typed read model, bounded paging, scoped membership and requested summaries behind existing contracts in an isolated testing checkout. Retain native detail decoding, source eligibility, provenance and annotation behavior. Qualify all nine UI actions and scientific fidelity before merging or installing. Adaptive preferences, action logging and specialized aggregate caches are subsequent measured work, not prerequisites that should expand the first integration indefinitely.

Use the [improvement traceability ledger](../dev/metadata-index-handoff-2026-10-01/IMPROVEMENTS.md) to retain the earlier cache/policy/catalog safety fixes as well as the latest measured query changes. Its status labels distinguish prototype changes, regression controls and proposals.

Use the [storage benchmark contract and baseline](../dev/metadata-index-handoff-2026-10-01/STORAGE.md) with the real-million speed benchmark. A faster mapping that grows metadata disproportionately is a regression requiring investigation. Read-only H5 inspection now projects approximately 248 GB of equivalent recording files, with the measured 8.303 GB SQLite assets at 3.35% of that denominator (6.29% versus projected compressed response payload). The projection is not physical million-record storage; the full canonical project footprint and intermediate-scale growth curve remain unmeasured.
