This is a plausible explanation of the timing pattern, not a measured attribution of the entire extra 2.87 seconds: no per-stage miss/match counters were recorded. It strengthens the case for preparing an exact predicate view once and passing its authority to the first page, rather than independently rebuilding it. ## Existing metadata layers, and the actual gap

The layers are already substantially separated. The following are descriptions of current code, not new tier names that the app implements.

| Current representation | Contents and use | What still costs work |
|---|---|---|
| Registered core rows and `typed_core` | Identity, source, cell/block/group/protocol relationships, date/order, labels and type | `service.rows` still retains all registered core row dictionaries. Scope creation can enumerate or sort them. |
| Complete eligible field dictionary and epoch/value relation | Field definitions, canonical values, typed numeric/text/equality indexes and reverse field/value→epoch links | Supplying a large scope can rebuild a temporary identity relation; predicates and requested distributions still execute against it. |
| Lazy detail blobs | Full recorded detail, including shared ancestry, decoded when requested | Selected detail/export/reconstruction needs the appropriate bundle; it should not become a prerequisite for opening a page. |
| Scoped derived results | Exact predicate membership, tree grouping, counts/facets | Their useful lifetime is often longer than one request, but reuse requires proof of unchanged ownership and authority. |

The native store already separates `row_json`, `detail_blob`, and the field/value relation. The typed sidecar adds indexes over all eligible fields rather than a small whitelist. Native `_page` already uses a `sort_rank` keyset and a materialized, limited identity subquery before joining wide row JSON. “Add keyset pagination” and “delay decoding until after LIMIT” therefore describe existing behavior, not the proposed improvement. ([Native schema](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/disco/metadata/disk_index.py#L91), [typed schema/indexes](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/disco/metadata/typed_index.py#L129), [bounded page](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/disco/metadata/typed_index.py#L444))

The current core indexes include chronology and cell/block/group/protocol child order; there is no dedicated cell-type B-tree. Generic typed dictionary indexes do not ensure that a core-column shortcut has an optimal access path for a particular cell-type/date/protocol conjunction. Check selectivity and the actual query plan before adding a composite index. Indexed core metadata is not evidence that every common query is optimally indexed. ([Current index definitions, lines 181–204](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/disco/metadata/typed_index.py#L181))

The earlier 28-preferred-path experiment did not materially improve common queries and regressed some uncommon ones. Its corrected recommendation is to retain the complete typed index and target requested summaries and structural scope. Treat that result as evidence against deleting uncommon indexed fields, not against keeping common navigation projections compact. ([Recorded correction](metadata-priorities-2026-10-01.md#metadata-priorities-and-lazy-scientific-detail))

“All metadata remains accessible and queryable” needs a precise scope. The current eligible catalog intentionally omits long arrays, large values and sufficiently deep paths; some descriptive metadata is selected explicitly. Lazy full-detail access does not make those omitted values queryable. Preserve every existing queryable field now. If universal raw-metadata querying is required, add a separate exact, on-demand path with explicit operators and cancellation for these cold fields; never interpret an unloaded value as missing or silently drop it from a query. That is a functional extension to the existing catalog, not a performance claim. ([Current extraction limits, lines 222–244](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/disco/navigation/tree.py#L222))

## Algorithm 1: retain an exact prepared scope relation

**Target:** repeated identity hydration and admission for an already accepted protocol/search view. `typed_scope` turns bound membership into UUIDs on every read; each cloned reader deletes and refills `supplied_scope` by looking up those UUIDs. Search preview additionally enumerates eligible tree rows and returns the complete sorted membership with fingerprints. These operations are different from fetching 60 visible rows. ([Scope construction](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/disco/metadata/explore_queries.py#L243), [identity hydration](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/disco/metadata/typed_query.py#L155), [search preview](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/workspace_service.py#L1135))

**Representation:** a generation-owned relation containing `(view_id, epoch_id, sort_rank)`, with uniqueness on `(view_id, epoch_id)` and ordered access on `(view_id, sort_rank)`. Prepare it once after exact membership admission. A view descriptor identifies its source, binding, predicate and annotation authority. Subsequent pages seek within this relation, select at most `limit + 1` ordinals, and use the existing bounded row decoder. Reuse an immutable integer membership vector as an alternative where it avoids SQLite ownership complexity; compare both, not just their asymptotics. A new connection cannot reuse another connection's temporary table, so the implementation must deliberately choose a pinned reader owner or an immutable attached artifact rather than accidentally recreating the table.

This proposal applies established multi-column/covering-index and keyset techniques to **scope reuse**, where this app still repeats work. SQLite documents that suitable index order can combine selection and ordering and that covering indexes avoid extra table lookups. Its row-value documentation explains why scrolling from the last key avoids work proportional to the skipped prefix. Neither source establishes a timing for this application. ([SQLite query planning](https://sqlite.org/queryplanner.html), [SQLite scrolling windows](https://sqlite.org/rowvalue.html))

Let `N` be registered epochs, `M` the admitted view membership and `K` the page size. Current hydration is `M` UUID lookups/inserts per reader; preparation pays that once. With a verified ordered relation, a warm page can seek and visit roughly `O(log M + K)` relation entries before bounded decoding. Additional predicates can still inspect many candidates unless their matched membership was prepared too; the proposal does not make arbitrary residual predicates constant time. Full membership export remains `O(M)` and must remain exact.

Integer membership payload is roughly 4 or 8 bytes per member depending on ordinal width; SQLite rows, indexes, UUID mapping, allocator overhead and file pages add more and must be measured. Bound retained views by bytes and count, pin active readers, evict inactive views, and rebuild explicitly after eviction. Do not keep a separate million-entry UUID object graph for every click.

**Admission and invalidation:** bind the relation to the exact project/index owner and generation, source eligibility revision, frozen protocol binding revision, canonical predicate/filter, and annotation revision when relevant. Carry opening and closing checks across page reads. A changed generation, source relink, recipe, annotation predicate or owner invalidates its dependent view. A new layout can reuse exact membership while rebuilding layout order. TTL, object identity, collection length and a checksum that omits structural changes are insufficient proofs. Custom providers retain their existing implementation unless they explicitly provide an equivalent immutable publication contract.

**Falsifiable experiment:** compare current native reader hydration with one prepared relation at 1k/20k/100k/1m members, first/second/deep pages, broad and selective predicates, and view returns. Record prepare time, subsequent scope-admission time, entries visited, decoded-row count, p50/p95 wall time and retained bytes. Keep `K = 60`, output order and UUID/fingerprint receipts identical. A successful warm page must stop rehydrating `M` UUIDs; if it still scans or inserts `M` members, this algorithm has not been implemented. Inspect actual `EXPLAIN QUERY PLAN` and runtime counters; do not assert planner output strings as a stable API. ([SQLite EXPLAIN guidance](https://sqlite.org/eqp.html))

## Algorithm 2: ordered prefix nodes with contiguous leaf ranges

**Target:** tree navigation repeatedly groups rows into bucket lists, traverses ancestors, sorts the selected leaf and searches linearly for anchors. The current cache bounds retained data, but comparing the full fingerprint dictionary on a cache hit is still linear. A compact index can replace repeated tree assembly only after reliable immutable structural publication is established. ([Grouping and scope validation](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/disco/navigation/tree_pages.py#L253), [path/leaf/anchor work](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/disco/navigation/tree_pages.py#L520))

**Representation:** for one active split layout, maintain one vector of admitted epoch ordinals ordered by canonical split keys followed by the existing leaf chronology. Store compact prefix nodes containing the parent, child-array offset/count, and first/end offsets into that leaf vector. Store each distinct field/value key once. Branch membership is a slice, not a copied list at every depth; its visible epoch count is `end - first`. A path-to-node map resolves known paths. An optional inverse ordinal→leaf-position vector plus parent links supports anchor reveal. This is a prefix tree with compressed-array storage; the familiar `indices[indptr[i]:indptr[i+1]]` construction illustrates the offsets/slices principle, without requiring a SciPy dependency. ([SciPy CSR representation](https://docs.scipy.org/doc/scipy/reference/generated/scipy.sparse.csr_matrix.html))

For `D` split levels and `G` prefix nodes, retained arrays are `O(M + G)`. A uint32 leaf vector costs 4 MB per million members; its optional inverse vector adds another 4 MB, before node/value/dictionary overhead. Building all canonical keys is `O(MD)` and sorting can cost `O(M log M × D)` with tuple comparisons; exploit existing order only after demonstrating equivalence. After preparation, a path page can resolve `D` nodes and emit `K` children or leaves without regrouping all `M` rows. Anchor lookup becomes bounded by mapping and depth. Output construction still costs `O(K)`.

High-cardinality fields can make `G` approach `MD`; do not precompute every possible layout or every metadata field. Estimate and measure actual bytes, refuse retention beyond the current bounded-cache policy, and use on-demand prefix construction or the existing fallback. Distinct-cell, duration, annotation coverage and facet summaries are not implied by the leaf count; compute those only when a visible feature asks for them. For complete branch selection, emit the exact canonical DFS membership from the slice, preserving current limits and all-or-nothing acceptance.

**Admission and invalidation:** the layout owner must cover exact admitted membership plus every field used by grouping, labels, chronology and ordering. Current mutable test/custom rows can change cell/date/block values in place, so index generation or fingerprint identity alone cannot authorize reuse. Either publish an immutable native structural snapshot with a new revision on every such change or retain exact mutation checks/fallbacks. Recorded split values remain under sealed-index authority. Annotation-driven membership invalidates its dependent layout. Closing authority must still reject mid-request replacement.

**Falsifiable experiment:** use the existing renderer/tree oracle to compare every emitted key, missing bucket, order, count, ancestor offset, anchor and selected UUID against the proposed layout. Cover default and recorded/joint splits, 1k/20k/100k/1m scopes, skewed and singleton branches, layout changes, in-place mutations, custom providers, cancellation and byte-budget refusal. Measure cold build separately from five same-view expand/next/anchor sequences. Success requires no full-membership regroup/sort on a warm branch page and exact output equality; a fast stale layout is a failure. Re-run the unchanged workflow after the native experiment.

## Algorithm 3: typed posting intersections for hot predicates

**Target:** recurring cell-type/date/cell/history predicates and requested high-level distributions. The app already has a field/value→epoch inverted relation and typed value indexes, so begin by measuring its existing query plan. An additional posting format is justified only if it reduces the full query path after scope preparation; it is not a reason to replace the complete eligible-field index. ([Existing reverse index](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/disco/metadata/disk_index.py#L97), [typed predicates](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/disco/metadata/typed_query.py#L35))

**Representation and execution:** map each admitted epoch UUID bijectively to a generation-bound integer ordinal. For selected hot field/value pairs, store sorted postings or Roaring sets. An equality query retrieves a posting; numeric/date ranges combine the postings of exact eligible dictionary values; conjunction intersects with the source/bound-membership universe, disjunction unions, and negation subtracts from that exact universe. Emit matching IDs in the existing chronology, materializing row JSON only for the displayed page. Compare against SQLite with appropriate existing indexes and, only where query plans support it, a measured `(cell_type, sort_rank)` index. Do not add every column permutation.

Roaring partitions integers into containers and uses array, bitmap or run representations; its layout can help different densities, but is not uniformly smallest or fastest. Sorted integer arrays remain a useful alternative for very sparse/high-cardinality fields. A dense bitmap costs `N/8` bytes (125 kB at one million epochs) per posting; an uncompressed uint32 list costs `4m` bytes for `m` members. Roaring adds container/serialization overhead and can save space for suitable density/runs. Measure the field distribution rather than importing paper speedups. ([Roaring paper](https://arxiv.org/abs/1603.06549), [format specification](https://github.com/RoaringBitmap/RoaringFormatSpec))

Sorted-array intersection is linear in input lengths, with possible skew-aware searches. Bitmap intersection operates by machine words/containers; its work still grows with the represented set. Constructing hot postings costs at least reading their epoch/value links, and materializing `R` result IDs costs `O(R)`. For a requested facet, `cardinality(scope ∩ posting)` can avoid constructing its full intermediate membership, but requesting thousands of facets remains expensive. CRoaring exposes intersection-cardinality operations; that is a capability to evaluate, not a selected Python/package dependency. ([CRoaring API](https://github.com/RoaringBitmap/CRoaring))

Preserve existing typed equality, including boolean-versus-number behavior, exact wide integers, arrays, null and missing. Tree grouping keys and predicate equality are not interchangeable. Substring search still needs dictionary evaluation or a separately verified text index; bitmaps alone do not solve it. Rare fields stay queryable through the complete current index; requested cold fields must not disappear. Hotness changes physical acceleration only.

**Reusable summaries and changes:** cache or prepare only a visible overview, explicitly saved history predicate or active scope's requested facet set. A compact result receipt should carry the matched membership and requested sufficient statistics. Immutable recorded metadata permits reuse until its generation changes. Annotation overlays can update relevant postings only with a trustworthy change stream covering additions, removals, ownership moves and relinks; otherwise invalidate and rebuild. Incremental view-maintenance research supports deriving changes to stored results, but introducing a general engine is not the first step here. ([DBToaster paper](https://vldb.org/pvldb/vol5/p968_yanifahmad_vldb2012.pdf))

**Falsifiable experiment:** compare native SQLite, sorted postings and Roaring over the same real eligible fields and exact predicate oracle. Cross low/high cardinality with dense/sparse/skewed matches, source scopes, 20k frozen membership, broad/rare fields and requested/no summaries. Record build time, storage, cold/warm latency, intermediate bytes and exact UUID equality. Repeat after metadata replacement, annotation removal, source exclusion and generation turnover. Reject a posting candidate that merely moves its full cost to view entry, exceeds the byte budget, or changes any result. Run the unchanged custom-adapter workflow too, while reporting that native matcher acceleration is not exercised there.

## Display-driven summaries and next experiment order

The user's distinction is sound: cell type, date, cell identity, relationships and membership are frequent navigation inputs; much other metadata serves inspection, reconstruction or export. Optimize their representations and demand separately. Avoid inferring “unused” from “not displayed”: predicates and scientific reconstruction can require a field that is absent from the UI.

The current code already offers requested facet summaries and a summary-free search-preview option. Extend reuse around explicitly requested high-level overviews, without computing every field distribution on entry. A field registry listing definitions/types/operators is not the same as computing per-field scoped summaries. Likewise, a compact page's cell/type/source information is not the full scientific metadata blob. ([Requested facets](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/disco/metadata/typed_index.py#L464), [summary-free preview](https://github.com/maxwellsdm1867/Rieke-OS/blob/77db8b024901af572143295111c127ccde625cdd/python/workspace_service.py#L1143))

The late-materialization literature motivates operating on compact attributes and identities before reconstructing rows, while also showing that physical layout alone does not reproduce a whole columnar executor's performance. That supports testing these narrow structures, not promising that a database replacement will fix the app. ([Abadi, Madden and Hachem, SIGMOD 2008](https://www.cs.umd.edu/~abadi/papers/abadi-sigmod08.pdf))

1. Instrument native scope hydration/admission, matching, grouping/sorting, decoding, serialization and queue wait separately. Retain the workflow fixture's current meaning.
2. Prototype prepared membership and compact active-layout slices against exact oracles. These directly target repeated scope/page work without removing uncommon query fields.
3. Compare posting formats only after those costs are isolated. Begin with the user's common predicates and saved history overviews; demand a measured benefit over current SQLite.

Every comparison needs the same source identity, fixture/input digest, warm/cold definition, result digest and explicit custom/native path label. Report preparation and repeated-interaction costs separately, with peak/retained memory and byte-budget behavior. No algorithm is qualified for a release or real large-H5 use by this research note.
