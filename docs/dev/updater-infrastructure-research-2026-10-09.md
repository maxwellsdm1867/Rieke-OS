# macOS updater infrastructure research — 2026-10-09

## Findings and recommendation

**Disco should minimize work after the user chooses Restart, while retaining a real verification boundary before replacement.** Treat download/preparation time, restart-click latency, and actual application downtime as three separate measurements. The strongest pattern found is Sparkle's explicit preparation stage before it presents an update as ready to relaunch. This is an architectural recommendation, not a measured ten-second promise. [Sparkle installation design](https://github.com/sparkle-project/Sparkle/blob/2.x/Documentation/Installation.md)

For the immediate unsigned-testing release, retain the existing coordinator, fix replacement/recovery failures, consolidate duplicate reads, and expose meaningful preparation phases. For the sustainable public distribution path, qualify **Developer ID signing + notarization + the already-pinned electron-updater/Squirrel.Mac stack**. Do not introduce a second native updater framework merely for speed: signing is already a prerequisite of the Electron macOS update API, and electron-builder supplies release metadata and distribution integration. [Electron 44.5.0 contract](https://github.com/electron/electron/blob/v44.5.0/docs/api/auto-updater.md), [electron-builder v26 update guide](https://www.electron.build/v26/docs/features/auto-update/)

**Slack's approximately ten-second update is the user's observation, not a verified benchmark.** Slack's official instructions document Check for Updates, Restart to Apply Update, and an update badge. They do not establish the amount of background work, current internal updater implementation, bundle size, cache state, or a restart-time guarantee. It would be unsupported to claim Slack skips integrity checks or uses a particular current macOS delta engine. [Slack's update instructions](https://slack.com/help/articles/360048367814-Update-the-Slack-desktop-app)

## Work before Ready versus work after Quit

| Infrastructure | Preparation while app runs | Quit/replacement behavior and limits |
| --- | --- | --- |
| Electron 44.5.0 / pinned Squirrel.Mac | Downloads and extracts an update, verifies its signature against the current application, and prepares a ShipIt request. | Electron's `quitAndInstall()` closes windows and quits; a separate helper handles installation. Application shutdown needs explicit integration because update quit ordering differs from ordinary `before-quit`. [API](https://github.com/electron/electron/blob/v44.5.0/docs/api/auto-updater.md), [pinned updater implementation](https://github.com/Squirrel/Squirrel.Mac/blob/8d808803bc89ec0e2aa1450474856dfee3b00c6b/Squirrel/SQRLUpdater.m) |
| electron-updater 6.8.9 | Downloads the ZIP and serves it locally to Electron. | Its `update-downloaded` precedes native preparation completion. `quitAndInstall()` waits for native readiness; `autoInstallOnAppQuit=false` defers native preparation until requested. [Pinned MacUpdater](https://github.com/electron-userland/electron-builder/blob/electron-updater%406.8.9/packages/electron-updater/src/MacUpdater.ts) |
| Sparkle 2 | A launchd-managed installer extracts and validates, performs stage-one preparation where possible, then informs the user driver that relaunch is ready. | A quit request may be delayed/cancelled by the app. Final replacement waits for termination; a progress agent can display a long install and relaunch afterward. This is a useful design model, not evidence that every failure rolls back or every app starts successfully. [Installation design](https://github.com/sparkle-project/Sparkle/blob/2.x/Documentation/Installation.md) |

The pinned Squirrel installer still copies into its own temporary directory and verifies the candidate there; it checks that the target is not running immediately before acquiring/replacing it. It persists an owned-bundle record and has an abort path restoring that bundle. Thus a maintained updater is not “no checks after quit.” Its documented source also does not establish Disco-specific database or scientific-session readiness. [Pinned installer](https://github.com/Squirrel/Squirrel.Mac/blob/8d808803bc89ec0e2aa1450474856dfee3b00c6b/Squirrel/SQRLInstaller.m)

Sparkle advertises atomic-safe installs; that is not a guarantee of crash-free application startup, nor evidence of automatic rollback for arbitrary application defects. Keep those acceptance criteria separate. [Sparkle project](https://github.com/sparkle-project/Sparkle)

## Checks and trust boundaries

**Authenticity and transport integrity are different.** Electron's native macOS updater requires a signed application; the pinned Squirrel updater validates the candidate against the current app's signing requirement. electron-updater's download path passes release SHA-512 metadata to the downloader and validates cached paths. A checksum obtained with an unsigned release descriptor is useful integrity evidence, but is not a Developer ID publisher identity. The latter distinction is our security interpretation, consistent with Disco's explicit testing trust label. [Pinned Squirrel updater](https://github.com/Squirrel/Squirrel.Mac/blob/8d808803bc89ec0e2aa1450474856dfee3b00c6b/Squirrel/SQRLUpdater.m), [AppUpdater 6.8.9](https://github.com/electron-userland/electron-builder/blob/electron-updater%406.8.9/packages/electron-updater/src/AppUpdater.ts), [Disco testing validator](../../desktop/updates/testing-update-validation.cjs)

Sparkle requires cryptographically signed update archives and provides EdDSA signing tooling. Its feed supports minimum OS requirements and machine-readable build versions. Those framework checks do not replace Disco's own MySQL/workspace compatibility policy. [Sparkle publishing](https://sparkle-project.org/documentation/publishing/), [Disco compatibility checks](../../desktop/updates/testing-update-validation.cjs)

For normal public direct distribution, prepare Developer ID signatures for all shipped executables, hardened runtime, secure timestamps, and notarization; staple the resulting ticket. Apple distinguishes these from ad-hoc/local signing. Enabling `notarize:true` in build configuration alone does not prove a shipped artifact was accepted. Verify the actual candidate and its notary logs. [Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Apple Developer ID overview](https://developer.apple.com/developer-id/)

Do not copy quarantine-clearing implementation details from signed frameworks into Disco's unsigned-testing path. Sparkle's security history includes hardening specifically at downloader/installer handoffs, demonstrating that ownership and repeated validation at process boundaries are substantive security work. [Sparkle security/reliability history](https://sparkle-project.org/documentation/security-and-reliability/)

## Delta updates

electron-updater **6.8.9 supports differential macOS ZIP downloads** using cached `update.zip`, with full-download fallback and caching for subsequent updates. This transfer optimization does not eliminate native preparation. Disco's custom testing coordinator does not use it. [MacUpdater 6.8.9](https://github.com/electron-userland/electron-builder/blob/electron-updater%406.8.9/packages/electron-updater/src/MacUpdater.ts), [testing coordinator](../../desktop/updates/testing-updater.cjs)

Sparkle offers signed per-source-version binary deltas, generated by its appcast tool, with a full-archive fallback if a matching patch is missing or cannot apply. Old clients must understand the selected patch format. Recommendation: use an established framework's supported delta mechanism after the full-update path is qualified; do not write a bespoke patch engine for this repair. [Sparkle delta contract](https://sparkle-project.org/documentation/delta-updates/)

## What Disco can consolidate or move

These are recommendations derived from the local call graph, not claims that all are already implemented or measured. [Testing coordinator](../../desktop/updates/testing-updater.cjs), [testing validator](../../desktop/updates/testing-update-validation.cjs), [helper](../../desktop/testing-install.cjs), [bundle installer](../../desktop/bootstrap.cjs)

| Work | Recommendation |
| --- | --- |
| SHA-256 and SHA-512 over the same archive | Compute both during one physical read. Keep both expected digest checks. |
| Resource hashes followed immediately by whole-bundle hashes | Capture one inventory/read pass and use it for both proofs, binding the parsed manifest and its raw digest to that scan. |
| Coordinator archive check directly followed by a built-in validator's identical check | May consolidate within the same invocation if one guaranteed check remains; injected validators must retain the coordinator's independent protection. |
| Adjacent deep-signature calls on the same source | Share the result inside one controlled operation; do not export it as indefinite install authority. |
| Extraction, candidate resource audit, copy into destination-volume staging | Move into the preparation interval before Ready, with private ownership, persisted identity and explicit expiry/revalidation rules. This needs a designed handoff, not a status-label change. |
| Checks after user delay, service drain, actual exit, or copy | Preserve the boundary proof. Optimize its implementation; do not assume yesterday's Ready hint authenticates today's bytes. |
| Installed runtime corruption or extra bytecode files | Diagnose and prevent app-bundle mutation. Do not ignore files, silently reseal the app, or treat a damaged installation as verified rollback material. |
| Scientific lifecycle | Keep draft persistence, writer closure, exact service/process termination and format compatibility under Disco's ownership regardless of updater library. |

## Minimal sustainable route

1. **Finish the testing-path repair first.** Qualify authentic published old→new bundles in an isolated installation; retain exact diagnostics and test failures after copy, rename, verification, rollback-receipt persistence and launch request. An `open` success is only a launch request: add an exact-build startup acknowledgment if claiming successful relaunch. Keep scientific-data readiness a separate signal. This is a Disco acceptance recommendation, grounded in its current helper boundaries. [Helper](../../desktop/testing-install.cjs)
2. **Make Ready truthful.** Show Downloading, Preparing, Ready, Closing work and Restarting. Use byte percentages only where measurable; show phase/elapsed time for verification rather than an invented percent. Retain a concise last failure after restart and private detailed diagnostics. electron-builder provides download-progress events; Sparkle demonstrates delayed installer progress UI. [electron-builder events](https://www.electron.build/v26/docs/features/auto-update/), [Sparkle installation design](https://github.com/sparkle-project/Sparkle/blob/2.x/Documentation/Installation.md)
3. **Qualify the existing signed path, rather than replace it wholesale.** Provision signing/notarization, publish the ZIP and compatible `latest-mac.yml`, then test the exact pinned libraries. Decide deliberately whether ordinary Quit may install: Disco currently disables that policy, which defers Squirrel preparation. Changing it affects lifecycle authority and requires review. If it stays disabled, label native preparation honestly rather than promising an instant restart. [Disco signed owner](../../desktop/updates/updater.cjs), [electron-builder configuration](https://www.electron.build/v26/docs/features/auto-update/), [MacUpdater implementation](https://github.com/electron-userland/electron-builder/blob/electron-updater%406.8.9/packages/electron-updater/src/MacUpdater.ts)
4. **Keep releases immutable.** Ship a higher version for a fix; do not replace the bytes of published 0.1.10 and expect existing 0.1.10 clients to update. electron-builder explicitly documents that a corrected staged release needs a higher version. GitHub immutable releases lock assets and tags after publication; assemble a complete draft before publishing. Whether this repository enables immutability was not inspected or changed. [Version guidance](https://www.electron.build/v26/docs/features/auto-update/), [GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases), [GitHub release workflow](https://cli.github.com/manual/gh_release_create)

## Evidence required before a speed claim

Measure separately: release check, network transfer, extraction, validation bytes/time, prepared wait, restart-click→quit, quit→new app first window, and first window→scientific project ready. Compare identical hardware, filesystem, bundle pair and cache state. Include first install without delta cache, cached full update, tampered cache, damaged old installation, interrupted helper and launch failure. Report the authentic pair and seams; a synthetic version-overlay fixture or intercepted launch does not establish public 0.1.9→0.1.10 success. These are proposed Disco measurements, not timings obtained from Slack or the upstream projects.

This research changed documentation only. It does not claim signing, notarization, updater migration, native rollback qualification or a ten-second restart has been completed.
