# Implementation scope after adversarial review

2026-10-13. Addresses [review items 1–8](ui-cache-adversarial-review.md). These decisions narrow the first delivery rather than pretending that a universal persistent revision manifest already exists.

1. **Combined source:** merge local startup `86e395a` (which contains release `add33d1`) into this isolated branch based on newest UI `386e72d`. Resolve actual merge conflicts, retaining both icon UI and release behavior. Apply only the intended managed-library `4a9d247` delta. Record integration identity and checks before changing cache behavior; preserve original branches/checkouts.
2. **Destination table:** plain project overview/stores/protocol returns reuse their destination. New search workspaces retain distinct draft/undo identities. Explicit inspection, export recipe and merge intentions retain distinct activation semantics. Back/forward addresses its original view. Each retained instance owns immutable-route callbacks; later active-route callbacks cannot overwrite a hidden view's snapshot.
3. **Desktop ownership:** use a registry of retained scientific content with a verified project/backend binding and separate native host. Every sender/origin/main-frame check, authenticated request, draft acknowledgement, download, dialog and quit path uses exact registered ownership. Active commands/clipboard target visible contents. Crashed/retired content is not interchangeable with another project.
4. **Startup:** only confirmed active-content activation/save may update the last active project. Hidden saves continue persisting their own drafts but never choose startup destination. Test late hidden save and quit.
5. **First disk resource:** persist only a last-good project overview presentation in a bounded separate SQLite store. It is explicitly not current authority after process restart. Capture only a successfully completed overview under its existing read owner, strip action/revision capabilities from the stored presentation, and validate physical project namespace, schema, bounds and checksum before loading. Do not build an unproven universal generation counter.
6. **Restart/restore freshness:** a disk snapshot is presentation-only. Every new process performs one canonical current overview read after the existing scientific startup/verification; cached counters cannot bypass that read. This remains conservative for same-path database restore with repeated UUID/incarnation/counter values. Cross-restart admission of mutable cached results as current, disk waveform caching and persistent source-contract hash narrowing are separate future optimizations, not claims of this delivery.
7. **Early hydration:** the lightweight project shell serves a bounded cached overview before heavy data initialization. The frontend keeps that Overview mounted and inert for scientific actions until current data is ready; project switching remains available. Canonical data replaces displayed values in the same view. If no compatible snapshot exists, use normal first-load behavior.
8. **Eviction:** begin with a small deterministic working set (three project contents, eight destinations) and preserve dirty/busy or uncheckpointed state above a soft cap. Desktop eviction requires successful existing draft flush; oversize/failed saves cannot cause silent data loss. Destinations must retain required filters/scroll/zoom/draft state or be kept resident. Scope/actor changes remain publication fences.

The core user outcome remains immediate unchanged navigation, preserving the last screen, and disk-backed restoration after restart. Full cold scientific initialization is not eliminated by a saved presentation. Refresh after committed changes updates affected values without destroying the live view. Existing source verification, action leases, frozen membership and accepted-operation recovery remain authoritative.
