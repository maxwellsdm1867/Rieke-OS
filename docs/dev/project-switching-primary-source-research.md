## What established implementations do

VS Code's `EditorPane` contract says that created editor widgets stay alive and are shown or hidden during ordinary use, with disposal at editor-group closure. Its `EditorMemento` separately keeps resource-URI/group-indexed view state in an LRU cache, serializes that cache, clears state when inputs are disposed, and handles moved resources. This is evidence for separating a live view's lifetime from visibility and for a bounded restoration layer; it is not evidence that VS Code keeps one renderer alive per entire project. [Microsoft source, `EditorPane` and `EditorMemento`](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/browser/parts/editor/editorPane.ts).

Electron provides `WebContentsView` to display a `WebContents`, including adoption of an existing one. Each web contents can be presented in only one such view at a time. The official example loads independent pages into views within one window. [Electron WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view). A view can be hidden using `setVisible(false)`; this is a visibility operation, distinct from destroying its web contents. [Electron View](https://www.electronjs.org/docs/latest/api/view).

React preserves state while the component remains at the same tree position and discards state when that component is removed. Merely revisiting a URL or reusing HTTP responses therefore does not constitute a React state cache. [React state preservation](https://react.dev/learn/preserving-and-resetting-state). React's `Activity` offers an alternative inside one renderer: retain component state and DOM while hidden, clean up effects, and recreate effects when shown. Hidden DOM can still have side effects, and children can render at lower priority in response to props. [React Activity](https://react.dev/reference/react/Activity).

## Recommended narrow direction for Disco

This recommendation is an inference from those APIs and the local architecture reported above: retain one project document per warm project, rather than reconstructing a document on every switch. Keep the existing separate backend origins and project-scoped frontend state. A desktop-owned registry would pair a project identity and backend instance with its retained `WebContentsView`. Switching A → B → A would change visibility, bounds, focus, and the active command target; it would not call `loadURL` or `location.assign` for an already valid view.

The warm view naturally retains navigation, expanded branches, scroll positions, trace buffers, selection, request caches, and unfinished controls. Retaining this existing state is a smaller conceptual change than inventing serialization for every frontend cache. It does, however, require a deliberate desktop lifecycle change and testing of menu dispatch, IPC routing, focus, resize, dialogs, and project closure. It is not just an HTTP cache setting.

Use a two-level lifetime:

1. **Warm project:** backend plus live document retained. Activation presents the existing view immediately.
2. **Evicted project:** only bounded, explicitly serializable UI state survives. Reopening can need document/data loads. The UI must not promise an instantaneous warm switch after eviction.

`Activity` is useful if Disco later hosts multiple project subtrees in a single renderer or wants to suspend individual panels. It is not a direct replacement for retaining documents on distinct localhost ports. It would first require explicit per-project API clients and state ownership, avoiding global active-project state leakage. Recreated effects would also need to avoid unconditional refresh-on-mount.

## Correctness and resource rules for that design

These are proposed Disco constraints, not claims that Electron supplies them automatically:

- **Stable identity:** key a warm entry by canonical project identity plus backend-instance identity, not display name or port alone. A port reused by a restarted or different backend must not inherit the old project's view authority.
- **Freshness:** preserve UI immediately when the same backend instance is healthy. Apply existing generation/revision checks to scientific reads and mutations. On background data changes, refresh affected data, not the whole document. On backend crash, project move/replacement, schema migration, or incompatible frontend revision, mark the entry invalid and recreate/reconnect explicitly. Cached display cannot establish mutation authority.
- **Background work:** hiding and throttling are not a complete suspension contract. Explicitly pause avoidable polling, trace prefetch, animation, and view-only subscriptions in inactive projects. Cancel only replaceable read work; never implicitly cancel an import, write, or export because another project became visible. Keep task ownership project-specific and surface completion on return.
- **Memory:** retain only a small measured working set, such as active plus two recent projects as an initial experiment, and use an LRU eviction policy for clean inactive views. That number is a proposal, not a measured optimum. Account for frontend trace arrays and backend caches separately; a view-count cap does not bound bytes. Record renderer/backend memory before fixing a byte budget.
- **Drafts and close:** switching is not closing. Do not auto-evict a view with unrecoverable drafts or ongoing scientific mutations. Either retain it or first preserve drafts through a proven project-scoped mechanism. Explicit close and app quit must consult all retained views, including hidden ones, before tearing down their backend and view. If all inactive views are protected, accept a documented soft memory limit rather than silently losing work.
- **IPC:** associate privileged actions with the sender's registered project identity and allowed origin. Do not resolve a delayed request from hidden project A against globally active project B. Retain existing preload isolation, sandbox, navigation, and permission restrictions for every created view.

Electron's `backgroundThrottling` concerns animations/timers and affects Page Visibility; disabling it for one web contents affects the host window's other web contents. Its `close({waitForBeforeUnload: true})` can honor unload prevention, whereas closing without that option destroys the contents without that protection. [Electron webContents](https://www.electronjs.org/docs/latest/api/web-contents). Electron explicitly requires closing child web contents when a `BaseWindow` closes; otherwise they leak. [Electron BaseWindow resource management](https://www.electronjs.org/docs/latest/api/base-window#resource-management). Electron also requires validation of IPC senders, including their origin. [Electron security: IPC senders](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages).

## What would demonstrate success

Use disposable projects and ordinary click-to-correct-result timings. Compare first open separately from warm A → B → A. For the warm case, verify the same web-contents identity, unchanged document-load count, retained tree/trace/scroll/draft state, and no replay of initial workspace bootstrap requests. Measure median and tail latency, memory growth, and inactive request rate. Test rapid repeated switching, completion of a background write, an external revision change, backend restart with port reuse, memory eviction, hidden dirty-view closure, application quit, and renderer crash. Preserve scientific action freshness and exact project identity throughout. A smooth display alone is insufficient evidence of a correct switch.
