# Renderer algorithms and demand-driven payloads — 2026-10-07

## Recommendation and evidence boundary

Across workflows, first prioritize shared, exact prepared membership/admission in the backend, because the awaited reads dominate the measured paths. The highest-leverage renderer/API companion is a **small, authority-bearing browsing descriptor and bounded page read that do not wait for overview aggregates**. Reuse that separation for main inspection, predicate-result inspection and incoming inspection. Follow it with one exact bounded incoming-selection read. Normalize/window the renderer only after measuring its CPU contribution; there are credible scaling hazards, but the present evidence does not make React rendering the cause of multi-second preparation or selection.

This is research, not an implementation or performance claim. No product files, active app, user data, or benchmark fixtures were changed; no benchmark was run. Code inspected at clean `77db8b024901af572143295111c127ccde625cdd`. The [stage4 receipt](../../benchmarks/results/stage4-workflow-candidate/receipt.json) measures clean **`812fe6db0cf20705a7c39065788fde9ca8c34243`**, not that later HEAD. A scoped Git diff confirms production frontend and workflow harness are unchanged between them; the frontend difference is a test expectation. Stage3 diagnostics measure `a6942215d418e505b76eb875bdd323e849ad10a8` and are separate evidence.

The fixture is one million project epochs, 20,000 active-protocol epochs, 100 incoming epochs, three ordinary samples, development React/Vite, headless Chrome 154, Apple M1 Pro. It mounts production components in an owned shell, **not full App session restoration or installed Disco**. DOM/RAF readiness and canvas calls do not establish compositor presentation. Three observations cannot establish p95 latency.

**Proposed tier boundary:** core linked record contains exact epoch/cell/block/group/protocol/source identities, ordering, membership receipt, hot date/cell/type keys, inclusion/annotation receipt and authorized stream locator. Cold metadata remains complete and source-linked, read by UUID and revision on explicit detail, cold-field predicate or export demand. Requesting a cold predicate must execute the exact field semantics over full relevant scope; lack of a hot index must not mean field absence. Export resolves complete metadata from the authoritative linked record, never a browser's subset projection/cache. Null/missing, typed equality, order, duplicate labels across cells and exact UUID membership remain unchanged. This projection change is useful independently of a database replacement.

## Three algorithm alternatives, ranked by leverage

### 1. Demand-driven request graph with bounded exact projections

Move browsing data requirements to the route/session operation so it can obtain a small descriptor plus fresh page, independent of expensive overview presentation. If identity is already authoritative, independent requests may run together; if it is not, use one backend-owned response carrying descriptor/page receipts from one admitted generation. Do not parallelize stale parent and fresh child reads and combine incompatible generations. React's documentation identifies parent-then-child fetching as a network waterfall and recommends hoisting/preloading/deduplicating requirements ([official useEffect guidance](https://react.dev/reference/react/useEffect#what-are-good-alternatives-to-data-fetching-in-effects)).

For selection, [incomingSelection.js:16–37](../../workspace-app/src/incoming-workbench/incomingSelection.js) currently visits cells and 60-row pages sequentially, validates complete membership and only then returns IDs. For S≤1000 IDs and Q pages this is Q dependent round trips. Prefer one bounded ID projection after a single admission, O(S) serialization, over simply increasing concurrency: parallel pages may still repeat expensive scope work or serialize on the server. Preserve the chosen cells' order, page order, duplicate/missing checks, revision/candidate binding and publication-after-completion. Reuse the existing exact resolver only if its ordering/scope semantics are proven equivalent; branch DFS order must not silently replace cell-list order.

Column navigation already has batching/attestation: [columnTreeReads.js:8–30,90–123](../../workspace-app/src/tree-ancestors/columnTreeReads.js). Warm target reads remain fresh; only nonterminal ancestors can reuse a lease. The benchmark's workspace request scope explicitly suppresses the inherited tree-read owner ([Inspector.jsx:45–46](../../workspace-app/src/epoch-browser/ui/Inspector.jsx)); its three-request expansion must not be reported as the universal installed cache path. First investigate whether known-capability bundled ancestors can avoid a fallback dependency for this exact scope. Do not cache terminal membership as if it were structural geometry.

Cold cost still includes exact admission and visible-page output; this design does not erase O(N) server membership work. Warm benefit would come from retained descriptor/normalized presentation and an exact fresh witness, not stale consent. Highest reuse: open/return, history navigation into inspection, predicate-result opening, incoming opening and selection.

### 2. Normalize admitted pages once, derive UUID lookup sets, isolate presentation updates

[InspectionCellTree.jsx:29–35,49–59](../../workspace-app/src/epoch-browser/ui/InspectionCellTree.jsx) validates rows against a `seen` array with `includes`, then copies the full prefix into each recursively appended page. With p rows/page and k retained pages (R=pk), one full render can perform O(R²) prior-membership comparisons and hold O(pk²) prefix references. This is a static worst-case growth analysis; the measured fixture mostly touches one/two 60-row pages. [ColumnTree.jsx:169–172](../../workspace-app/src/tree-browser/ui/ColumnTree.jsx) repeats selected-ID `includes` and cell `find` inside row rendering, and [IncomingTreeSelection.jsx:9–12](../../workspace-app/src/incoming-workbench/ui/IncomingTreeSelection.jsx) checks selected IDs again. R rendered rows and S selections yield O(RS) membership scanning, though S is bounded to 1000.

Use an immutable ordered page ledger keyed by **full receipt identity**, an epochById/cellById map, and a derived selected-ID Set. Validate each newly admitted page once against a generation-owned seen-ID set; preserve original ordinal/page receipt separately. Under typical hash-table assumptions admission becomes expected O(p), lookup expected O(1), and rendering O(R+S) when rebuilding the selection set. ECMAScript guarantees only average sublinear Set/Map access, not worst-case O(1) ([language specification](https://tc39.es/ecma262/multipage/keyed-collections.html#sec-set-objects)). A retained ledger remains O(R) metadata until an explicit bound is added.

Keep ordered UUID arrays as scientific selection authority; Sets are derived acceleration only. One mutable shared Set passed through concurrent renders is unsafe: admission belongs to an owner/controller with atomic immutable publication, not render-side mutation. Receipt changes retire the ledger. Do not replace the tree cache's typed canonical identity with JSON serialization; its contract distinguishes negative zero and exact generations.

[InspectionCellTree.jsx:107–129](../../workspace-app/src/epoch-browser/ui/InspectionCellTree.jsx) publishes navigation state on every scroll event; line 135 serializes all cell UUID/count pairs on render. Separate ephemeral scroll position from data/selection updates and checkpoint it at an appropriate cadence plus navigation/unmount flush, preserving restoration. Stable row props/memoized derived indexes can avoid repeat work, but blanket `useMemo` is not a cure. React recommends flat state to avoid duplicated nested records ([state structure](https://react.dev/learn/choosing-the-state-structure#avoid-deeply-nested-state)); memoization depends on unchanged dependencies and is only an optimization ([useMemo](https://react.dev/reference/react/useMemo)). Cold admission pays normalization cost; warm focus/highlight/scroll should not revalidate unchanged page DTOs.

### 3. Window the visible tree, independently of fetched-page membership

[InspectionCellTree.jsx:59,84–89,207](../../workspace-app/src/epoch-browser/ui/InspectionCellTree.jsx) retains appended epoch components and creates every cell branch, including cells under a collapsed date. Read paging is not DOM virtualization. Flatten the expanded presentation into stable date/cell/epoch keys and render viewport plus overscan. Fixed row heights permit constant-time visible index bounds; variable heights need measured size/prefix lookup. Keep loading frontiers and original membership/page receipts outside the viewport component. TanStack Virtual's official example renders only its virtual items in a container representing total size ([official introduction](https://tanstack.com/virtual/latest/docs/introduction)). This is an option to evaluate, not a dependency installation recommendation.

Expected mounted DOM cost becomes O(V) for V viewport/overscan rows instead of O(R+C) retained epoch/cell rows; building a flattened list can still cost O(R+C), and retaining fetched DTOs is still O(R). Thus combine windowing with option 2 and a deliberate retention bound; do not claim virtualization bounds all memory or backend work. Cold first-page benefit may be negligible. Greatest likely benefit is long scrolling sessions and large restored frontiers, currently outside fixed-workflow coverage.

Preserve keyboard reveal, focus outside viewport, screen-reader hierarchy/position, Load More fallback, stable scroll anchoring, exact Shift range across unloaded rows, and same-scope disabled retained selection appearance. A focused offscreen row may be pinned for focus only; it never replaces membership or authorizes actions. Unmounting a visual row must not revoke a still-needed shared read or restore old selection.

## Falsifiable experiments and objectives

These are proposed small experiments for a later authorized implementation, **not predicted speedups**. Preserve ordinary medians as comparison gates and run optional instrumentation separately. [React Profiler](https://react.dev/reference/react/Profiler) measures subtree `actualDuration` per commit, adds overhead and requires a profiling-enabled production build; it does not measure browser layout/paint or network CPU. Group nested profilers by commit and avoid double counting.

| 1 | Add diagnostic marks for descriptor admission, page request, response consumption and exact-ready; compare descriptor+page entry against current protocol-summary barrier on the same fixture. For demand tiers, record endpoint payload bytes and requests with metadata panel closed/open, live values off/on, split chooser closed/open, Overview visible/hidden, and cold-field query/export. Confirm cold-field query and export results match the complete source record exactly. Metadata demand must not precompute every field's distinct values just because the catalog is available.

Retain [ColumnTree.jsx:73–104](../../workspace-app/src/tree-browser/ui/ColumnTree.jsx) abort+serial+owner checks and [useEpochBrowserPage.js:13–27](../../workspace-app/src/epoch-browser/useEpochBrowserPage.js) keyed publication. Test transport that ignores abort. React transitions may keep presentation responsive, but do not reduce admission work and do not order arbitrary async requests automatically ([official useTransition caveat](https://react.dev/reference/react/useTransition#my-state-updates-in-transitions-are-out-of-order)). They cannot replace scientific freshness or permit interaction with old receipts.

No native/package qualification follows from this research. The next implementation should retain the repository's exact frozen/core/query checks and compare ordinary action timings before broadening claims.
