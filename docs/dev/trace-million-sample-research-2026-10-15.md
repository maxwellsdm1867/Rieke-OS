# One-million-sample trace latency: evidence and proposed experiments

Date: 2026-10-15. Scope: lossless full-trace delivery and drawing. This note does not authorize data decimation, altered scientific membership, relaxed provenance, new release promotion, or claims that a synthetic browser measurement is installed-app performance.

## Findings first

Keep the complete binary64 signal and make fewer representations of it. The smallest current change replaces decimal JSON samples with the versioned bounded binary transport after existing read admission. The next candidate is to retain NumPy arrays through reading and encoding, followed by a single-open bounded multiwindow H5 read if profiling supports it. Rendering changes need their own evidence; a million-sample Canvas path can remain expensive even after transport becomes fast. These are code-derived hypotheses, not universal speed guarantees. Current owners: [sample reader and batch](../../python/workspace_service.py), [binary encoder](../../python/workspace_trace_binary.py), [decoder](../../workspace-app/src/traces/traceBinary.js), [whole-trace composition](../../workspace-app/src/traces/readWholeTrace.js), [Canvas rendering](../../workspace-app/src/traces/ui/TraceViewer.jsx).

## Measured serialization, with limits

An owned deterministic 300,000-sample signal mixes two sinusoids and seeded Gaussian noise, plus finite binary64 boundary cases and signed zero. Seven serial measurements of the actual encoder gave these medians:

| Stage | Median |
| --- | ---: |
| Exact metadata recursive normalization | 26.08 ms |
| JSON decimal formatting after normalization | 89.33 ms |
| Complete exact JSON encoding | 115.76 ms |
| Binary encoding from already validated Python lists | 17.70 ms |

Encoded bodies were 5,805,392 versus 2,401,456 bytes. The binary payload matched the original little-endian float64 bytes exactly, including negative zero. Raw timings, both payloads and the independent bitwise receipt are in `/private/tmp/disco-binary-serialization-profile-v1/`; the standalone script is `/private/tmp/disco-trace-serialization-profile.py`. These observations exclude H5 reads, scoped authorization, HTTP, browser decode and Canvas painting. They are not a one-million-sample latency result and cannot be extrapolated into an acceptance claim.

A separate owned one-million-value real-H5/Flask diagnostic then exercised two bounded frozen batches. The backend agent recorded JSON median 351.23 ms versus binary 138.36 ms including the diagnostic client's Python decoding; the raw stage receipt is `/private/tmp/disco-trace-evidence-20261015/million-sample-stages.json`. This is still not a browser click-to-display measurement: SQL/metadata admission are explicit fixture doubles and there is no renderer or compositor. The browser result below must be reported separately.

## Code costs and safe next steps

The current H5 reader opens a file per window, validates epoch/stream/rate/count/units, reads a slice, converts quantity values to float64, rejects nonfinite values and calls `tolist()`. Batching uses one captured source plan and a final closing witness, but still calls this reader for each window. Binary encoding then validates those Python floats and copies them into `array('d')`. The browser decoder creates Float64Array views; one envelope is shared without another sample copy, while several envelopes are joined with a preallocated array. These are direct observations of the owners linked above.

1. **Keep arrays through the binary-only branch.** NumPy documents `tobytes()` as a copy of the raw memory, not a zero-copy operation. `astype(copy=False)` avoids a copy only when its dtype/order requirements are already satisfied; `frombuffer()` creates a view and needs explicit byte order for non-native data. Hypothesis: avoiding NumPy→Python-list→array conversion reduces CPU and allocations while retaining identical binary64 samples. Test bitwise output against the current admitted reader, with finite extremes, negative zero, mixed original numeric dtypes, truncated inputs and source changes. Do not downcast to float32 or claim original arbitrary int64 precision: the current reader already defines its numeric output by float64 conversion. [NumPy raw bytes](https://numpy.org/doc/stable/reference/generated/numpy.ndarray.tobytes.html), [astype](https://numpy.org/doc/2.2/reference/generated/numpy.ndarray.astype.html), [frombuffer](https://numpy.org/doc/2.2/reference/generated/numpy.frombuffer.html).

2. **One file open per existing bounded batch.** h5py basic slices already map to HDF5 hyperslabs. `read_direct` may avoid a slicing intermediate but requires a writable contiguous destination; compound fields and exact units still require validation. HDF5 chunks may cause more storage work than the selected logical range, so do not infer disk speed from requested bytes. Hypothesis: retaining a single file/dataset handle across at most five windows saves reopen/path/identity setup. Keep existing admission, bounds and final stat/publication witnesses. Compare identical windows serially on owned contiguous and chunked fixtures; record open counts separately from total read time. [h5py dataset operations](https://docs.h5py.org/en/stable/high/dataset.html).

3. **Keep typed views and avoid repeated presentation scans.** ECMAScript subarray semantics retain the original backing buffer. This supports the current decoder/zoom view design; it does not make the HTTP body or a join across two distinct envelopes zero-copy. The current painter computes a finite extent and issues a line operation for each sample. Hypothesis: reuse the already validated exact finite extent for the same buffer/window/axis identity, avoiding redundant scans on unchanged redraws. Test resize/theme/zoom/pan and stale buffer transitions; never reuse an extent from another interval. [ECMAScript typed-array subarray specification](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-%typedarray%.prototype.subarray), [current geometry](../../workspace-app/src/traces/ui/traceGeometry.js).

4. **OffscreenCanvas is a responsiveness experiment.** The HTML standard permits worker rendering with OffscreenCanvas, but its bitmap still reaches the placeholder canvas through rendering updates. Moving work does not prove lower click-to-complete latency. Test complete frame visibility, transfer/cancellation ownership, resize and CPU cost before adopting it. Sending an ArrayBuffer to another owner must not invalidate the main-thread cursor/zoom data. No worker rendering is implemented here. [HTML OffscreenCanvas](https://html.spec.whatwg.org/multipage/canvas.html#the-offscreencanvas-interface).

5. **WebGL all-vertex line strip, without selecting fewer points.** WebGL exposes vertex buffers, `vertexAttribPointer` and `drawArrays` with `LINE_STRIP`. A falsifiable proposal is to upload one vertex for each of the million samples, then submit a line strip rather than making a million JavaScript `lineTo` calls. Compute screen-relative coordinates from float64 values before converting display positions to float32; keep the original Float64Array for exact cursor, zoom and export. This preserves sample storage but does not promise identical pixels: shader precision, line widths/joins, anti-aliasing and GPU rasterization differ from Canvas. Test the coordinate error bound, isolated spikes, all vertices, device-pixel ratios, context-loss recovery, allocation failure and fallback; measure upload plus complete presented frame, not draw-call submission. No WebGL renderer is implemented. [Khronos WebGL specification, buffers/draw operations/context loss](https://registry.khronos.org/webgl/specs/1.0.3/).

## Pixel-based rendering proposals are a separate decision

The M4 paper selects first, last, minimum and maximum points per pixel-column interval and derives a result for a two-color line-rasterization model. Its anti-aliased discussion is not a blanket proof of identical output for Disco's current fractional-width Canvas stroke, device-pixel ratios, clipping, joins and isolated samples. MinMaxLTTB is explicitly a point-selection/downsampling method aiming at visual representativeness, not retention of every scientific sample in a plotted polyline. Neither paper licenses changing source data or analysis. [M4 primary paper](https://www.vldb.org/pvldb/vol7/p797-jugel.pdf), [MinMaxLTTB primary paper](https://arxiv.org/abs/2305.00332).

If the scientist later chooses a display-only overview algorithm, keep all one million samples for exact cursor reads, zoom and export; label any overview representation honestly. First compare actual Canvas pixels and exact extrema/isolated spikes against the current path at several widths, device-pixel ratios, axis ranges and gap patterns. Pixel differences must be reported, not hidden behind a claim of lossless samples. No such algorithm is implemented or automatically selected in this work.

## One-million-sample regression and measurement contract

The fixed workflow retains the existing 10,000-sample main and 300,000-sample frozen Workbench traces and adds a separate one-million-sample frozen Workbench action on a third owned H5 ramp. The production 500,000-sample maximum per batch remains unchanged; the million-value binary path requires two bounded requests, ten exact 100,000-sample windows. Every integer ramp value from 0 through 999,999 is checked, along with epoch, stream, source hash, rate, units, total, no-decimation flag, contiguous windows and frozen request revision. [Fixture](../../benchmarks/workflow/server.py), [browser oracle](../../benchmarks/workflow/browser.mjs).

The observer records the return from the real Canvas stroke and the stable DOM/RAF observation before that observation's correctness scan. It then verifies the complete payload using an independent framing decoder rather than the product decoder. First-observation oracle work can still delay the second RAF; the receipt reports verification time after the final observation and explicitly retains this instrumentation limit. A complete canvas call and DOM frame observation are not compositor-photon evidence. Keep matched current-harness baseline/candidate runs, ordinary samples separate from profiling, and raw failures. A small smoke verifies harness compatibility; the actual-million metadata workflow and native product test remain distinct qualifications.


## Observed browser smoke: complete million-value trace

The first current-harness Chrome smoke passed all 15 actions on the owned 1,000-metadata-row fixture. For the one-million-value trace it verified all 1,000,000 samples, two HTTP responses and ten windows: post-stroke observation 304.8 ms, second stable DOM/RAF observation 323.8 ms. The final observation's independent correctness scan took another 9.1 ms, recorded separately. The retained 300,000-value action measured 167.2/174.1 ms. Evidence: `/private/tmp/disco-binary-million-chrome-smoke/receipt.json` and its raw browser files.

Receipt flags are `status=diagnostic`, `smoke=true`, `epochs=1000`, `protocol_epochs=1000`, `samples=1`. Its source base is `4140371e72916b9dcfb9d390dd8e93d1c2088553` with the explicitly recorded uncommitted binary/harness changes; the recorded source fingerprint is `db6efb6d6fb3182324efd2a8a01f503e7935f053bfee713cfb0af8fee013be47`. This is one ordinary smoke sample of dirty source in development Chrome with real owned H5 reads and explicit SQL/metadata fixture doubles. It proves the complete million-value rendering path executes and passes correctness; it does not establish a median, a native-app latency guarantee, or equivalence to the user's recording.
