# Workbench algorithm research — October 7, 2026

**Recommendation:** build one attested, immutable prepared membership projection shared by queue, context, preparation, paging and selection. The expensive repeated unit is admission of the full frozen scope, even when the requested result contains only 60–100 epochs. Hot/cold metadata tiers should use this same publication identity. A bounded request-local read bundle is a useful first implementation step; a UUID-only recipe cache is not a safe substitute.

This is read-only research, not an implemented design or performance qualification. ## What the measurements establish

The fixed fixture has 1,000,000 project epochs, 20,000 active-protocol epochs and 100 incoming epochs. The [stage-four ordinary report](../../benchmarks/results/stage4-workflow-candidate/workflow.md) gives three-sample action medians:

| Action | Median | Requests | Remaining interpretation |
| --- | ---: | ---: | --- |
| Fresh preparation | 5,079.0 ms | 4 | Preparation itself plus a separately admitted initial page |
| Preparation receipt replay | 3,163.8 ms | 5 | The receipt lookup is already cheap; current context and page dominate |
| Return to prepared Workbench | 3,126.2 ms | 4 | Queue, context, then page are reconstructed |
| Select all 100 incoming epochs | 2,220.0 ms | 2 | Two sequential 60-row page reads, each admitting the full frozen scope |

The median fresh action's browser chain is queue at approximately 0.9–398.5 ms, preparation at 400.7–3631.2 ms, then incoming page at 3649.2–5060.3 ms. Metadata fields overlap the page. Its request-interval union is about 5,039 ms, or 99.2% of the action. The median selection has two approximately 1,097/1,101 ms page intervals; their union is about 2,198 ms, or 99% of the action. These are transport intervals, including server processing, lock waiting, transfer and response consumption—not pure CPU attribution. See the [browser samples](../../benchmarks/results/stage4-workflow-candidate/browser/action-samples.jsonl) and [request ledgers](../../benchmarks/results/stage4-workflow-candidate/browser/browser-requests-ordinary-0.json).

Stage-four module timers were off. The earlier [stage-three raw module ledger](../../benchmarks/results/stage3-workflow-candidate/server/requests.jsonl) identifies repeated work in the same Workbench implementation:

| Request | Full recipe `get` calls | Context builds | Query-result constructions | Useful timer observation |
| --- | ---: | ---: | ---: | --- |
| Fresh `POST /prepare` | 16 | 5 | 20 | Preparation operation median 3,298.7 ms across three calls |

For the six selection-page requests, median individual recipe read was 41.0 ms, context build 429.4 ms and actual `epoch_page` operation 47.1 ms. Context contains recipe/state calls; page-request time contains context and locking. **Do not add these nested timings or subtract their medians to invent an exclusive cost.** Across the three fresh actions, the raw ledger contains 93 recipe reads, 24 context builds and 78 query-result constructions. These are call counts, not a universal workload estimate.

The apparent long `/metadata/fields` request sometimes overlaps an equally long page request and sometimes completes in 0.2 ms. This is consistent with lock contention, but the ledger alone does not separate lock waiting from computation. It does not support labeling that entire interval metadata-catalog CPU time.

## Why a small read still does large work

Let `N` be the relevant main/candidate membership size, `P` the number of original proposals, `D` the actor's saved decisions, `K` the requested page/selection size, and `Δ` the changed membership or decision count.

1. **Stored recipes are fetched, copied and hashed repeatedly.** [ExplorerHistory.get:243–258](../../python/disco/decisions/explorer.py#L243) verifies the complete stored recipe, project/revision and summary on every call. [protocol_binding:93–101](../../python/disco/decisions/explorer.py#L93) separately copies its UUID-keyed cached recipe. The new specialized copier reduces constants; the membership size remains `O(N)`. The existing binding cache is not evidence that same-UUID storage edits are safe to ignore.
2. **Lock discovery also loads baselines.** [guarded:664–706](../../python/disco/workbench/workbench.py#L664) uses `proposal` and `origin_recipes` before acquiring annotation locks. Those helpers each hydrate candidate and baseline. In the one-origin cumulative fixture, discovery, opening context and closing context each read four recipes: cumulative candidate + baseline + original candidate + the same baseline again. That explains twelve reads per page. Dependency discovery needs candidate/origin ASTs, but currently pays for baseline verification too.
3. **Each context reconstructs multiple full maps and hashes.** [context:223–289](../../python/disco/workbench/workbench.py#L223) rebuilds main/baseline/candidate UUID-to-fingerprint maps, additions, intersections, conflicts, unavailable members, source eligibility, pending membership and the current-fingerprint digest. It revisits origins and additive lineage and hashes all saved actor decisions. A bounded output does not bound these scans.
4. **A revision request materializes the main query.** The context calls `state(protocol)` even when it already has a frozen main binding. [legacy_state:190–201](../../python/workspace_api.py#L190) constructs the query, calls `fingerprints`—which constructs it again at [workspace_service.py:684–686](../../python/workspace_service.py#L684)—builds all curation states and hashes the whole query/curation result. [query_result:708–746](../../python/workspace_service.py#L708) still visits every bound identity, cell and changed fingerprint. The native [materialized_state:381–389](../../python/workspace_protocol_state.py#L381) also invokes the full oracle; it is not a revision-only interface.
5. **Closing is another construction.** [finish:723–740](../../python/disco/workbench/workbench.py#L723) checks metadata generation and rebuilds `manager.context` to compare scope. This is necessary protection today. Removing the second call without an equivalent complete witness would weaken the scientific contract.
6. **Preparation repeats the same composition around its transaction.** [snapshot_authority:16–51](../../python/disco/workbench/workbench_pending.py#L16) builds original-proposal contexts and combines pending membership. [workbench_prepare:94–178](../../python/disco/workbench/workbench_pending.py#L94) invokes queue, snapshot, transaction authority, a second snapshot, a new context and its closing context. It also sorts/serializes the full new union recipe. Queue itself calls contexts across original proposals at [workbench.py:533](../../python/disco/workbench/workbench.py#L533). Costs grow with proposal history and repeated membership, not just new incoming rows.
7. **List selection repeats admission per transport page.** [loadIncomingSelection:16–37](../../workspace-app/src/incoming-workbench/incomingSelection.js#L16) sequentially enumerates each scoped cell in 60-row pages, verifies each complete page and finally checks exact total/uniqueness. The current 100-member case consequently performs two independently guarded full-scope reads.

The recipes already contain a narrow core: ordered `{uuid, metadata_hash}` membership, query/tree descriptions and provenance ([recipe creation:175–196](../../python/disco/decisions/explorer.py#L175)). They do not embed every rare metadata value per epoch. Therefore lazy cold metadata alone cannot eliminate the repeated 20,000-member copy/hash/map work.

## Ranked designs

### 1. Attested immutable membership publication — greatest shared benefit

Create a privately owned prepared projection for a complete input publication. It contains exact ordered membership, UUID lookup, fingerprints, source/cell references, verified recipe roots, lineage proof and static pending-set relationships. Separately bind the small changing actor/draft/annotation/source-authority vector. Queue, context, page and selection readers share this projection rather than converting the same recipes into Python maps repeatedly.

The relevant pattern is immutable publication with leased readers: construct a complete replacement, publish it atomically, and keep old storage alive until active readers release it. Linux's [RCU documentation](https://docs.kernel.org/RCU/whatisRCU.html) explains separating removal/publication from later reclamation; this proposal borrows the ownership/lifetime principle, not Linux synchronization primitives. A read-only Python outer wrapper is insufficient: [MappingProxyType is a dynamic view](https://docs.python.org/3/library/types.html#types.MappingProxyType), and nested mutable values still need ownership.

**Concrete admission algorithm:**

- Read a trusted publication vector `V0` covering project/server incarnation, schema/trigger contract, exact recipe storage, binding, metadata publication, source eligibility, relevant annotation scopes and actor draft. On a cold miss, fetch each unique recipe, verify its canonical seal and summary, and build the projection privately. Read `V1`; publish only if `V0 == V1` and the build was not cancelled.
- A warm request obtains a lease to that projection under a matching current vector, reads only requested members/fields, checks the closing vector and discards the response on change. Mutations still capture and attest their transaction authority independently. The read lease grants no merge/export consent.
- On an update, publish a new generation; never modify the old nested membership behind its published identity. Eviction releases only unused projections. Unsupported mutable/custom providers retain fresh canonical checks and current public semantics.

**Existing foundations and missing proof:** annotation authority [WATCHED:36](../../python/workspace_state_generation.py#L36) excludes recipes and Workbench tables. The recovery authority [TABLE_NAMES:34–38](../../python/disco/backup/recovery_generation.py#L34) includes them and attests instance, schema, triggers and clock, but its [token:330–339](../../python/disco/backup/recovery_generation.py#L330) performs substantial attestation and rejects an active transaction. It is a conservative starting witness, not a ready cheap Workbench token. One project-wide counter also over-invalidates on unrelated writes; measure before adding finer scope counters.

MySQL's [consistent-read documentation](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html) makes a critical distinction: repeated ordinary reads in one REPEATABLE READ transaction can keep seeing an old snapshot. Such a transaction can provide coherent SQL inputs but cannot prove that nothing changed before response publication. A closing check must observe current authority through the established locking/outside-transaction protocol, and Python metadata publication remains a separate dependency. Trigger-backed generation changes must commit with the data. [MySQL trigger semantics](https://dev.mysql.com/doc/refman/8.4/en/trigger-syntax.html) support transactional rollback, but [TRUNCATE bypasses DELETE triggers](https://dev.mysql.com/doc/refman/8.4/en/truncate-table.html); DDL/incarnation detection is mandatory.

**Complexity:** cold construction remains `O(total unique recipe membership + relevant metadata + D)`, with `O(N + D)` retained indexes per distinct publication and explicit byte/lease limits. A genuinely attested warm unfiltered page can approach `O(number of dependencies + K)` rather than `O(N)`; sorted/range lookup may add `O(log N)`. New filters or splits can still require a scan/build. A first source verification or changed-source import is not made constant-time. The current native proof still compares large mutable maps at [native_context:311–368](../../python/workspace_protocol_state.py#L311); it must not be relabeled constant-time.

**Hot/cold fields:** attach cell/date/cell type/source/order keys to the immutable core publication; retain UUID plus payload reference/fingerprint for all other fields. A rare-field query builds or consults a projection at that same generation; exports hydrate requested values lazily. Every field remains queryable, with exact type, missing-value, unit and ordering semantics. Cold metadata changes must still invalidate the appropriate fingerprint/publication. This field layout complements the shared admission primitive; it does not replace it.

### 2. Incremental pending-set and lineage maintenance on that publication

Represent each proposal's additions as `A_i = C_i \\ B_i`, and the cumulative pending view as `(union A_i) \\ M`, while preserving the separate fingerprint-conflict and lineage rules. Maintain UUID/fingerprint origin support counts, per-cell counts, source eligibility and actor decisions as keyed relations. An accepted UUID removes its pending visibility but does not erase its origin provenance; removing one overlapping origin must not remove an epoch still supported by another. Same-UUID/different-fingerprint rows remain an explicit conflict, never a winner chosen by last update.

[DBSP, PVLDB 2023, sections 4.2–4.4](https://www.vldb.org/pvldb/vol16/p1601-budiu.pdf) supplies the appropriate algebra: weighted relations model inserts/deletes; union and difference use distinct/threshold operations; maintaining distinct requires retained support state. Its analysis also warns that joins and initial state construction are not universally constant-time. Here the application-specific key is UUID, so indexed support-count/anti-membership updates can be proportional to changed keys rather than all historical recipes. This is a design inference, not a recommendation to install a streaming database.

Map it to `snapshot_authority`, `queue`, `_additive_lineage` and context's `incoming/pending/conflicts` calculations. Build verified per-recipe membership once, cache the proven lineage edge against its exact receipt and parent/child recipe roots, then update only affected contributions when binding, original proposals, fingerprints or actor decisions change. A missing delta, changed authority incarnation, inconsistent origin or schema change forces full canonical reconstruction/refusal.

**Complexity:** cold initialization remains `O(sum |C_i| + sum |B_i| + |M|)` and `O(number of distinct memberships + origin support + D)` storage. Indexed changes can be `O(Δ log N + affected outputs)`; large source or predicate changes can invalidate the entire projection. This primarily helps repeated prepare/queue/context work and histories with overlapping proposals.

The current full-union recipe format imposes a separate `O(N)` publication/serialization cost: it stores every member and computes canonical JSON SHA-256 ([recipes.py:21–23](../../python/disco/workbench/recipes.py#L21)). An arbitrary edit cannot update that existing flat hash by merely adjusting a counter. Content-addressed chunks or parent-plus-delta snapshots could share unchanged membership, following the object/root model described by [Git's object documentation](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects). That would require an explicitly versioned representation, exact ordered materialization, bounded ancestry/checkpointing and backup/export closure. Never change the meaning of an existing `content_sha256` or reseal historical receipts to claim compatibility.

### 3. Request-local admission fusion — useful bridge that moves the fixed fixture

Introduce a private, response-local verified recipe resolver/projection, with independent opening and closing reads. Fetch each unique recipe once per boundary, share intermediate maps within that boundary, and discover lock dependencies without hydrating unused baselines. Preserve custom method fallbacks. Baseline/parent/lineage validation must still happen before publishing any result; accepted-export routes currently do not run ordinary `manager.context` afterward, so they cannot inherit a blanket baseline-skipping guard.

Then expose a read-only bootstrap bundle containing current context and its first bounded page under one opening/closing admission. Replay/return currently admit these in separate requests. Add a bounded selection-ID read for the exact filtered incoming scope and requested cell ordering, capped at 1,000, instead of using metadata pages as the UUID enumeration protocol. Verify scope, complete count, order, uniqueness, exclusions and closing freshness. Do not treat client cell totals as membership authority. This combines the work already done independently; it does not reuse a durable preparation receipt as current context.

**Complexity:** still `O(N + K)` per independent request/bundle with mutable providers, but fewer full passes and fewer admissions. A cumulative page's unique-recipe resolver can reduce twelve recipe reads to six if discovery/opening share a verified response snapshot and closing independently rereads all unique dependencies; the smaller context-local-only version reaches nine. These are proposed structural counts, not measured wins, and sharing discovery needs a complete closing check of every consumed dependency. A single bounded selection request removes the second full admission in the 100-epoch fixture. This bridge alone will not make million-member warm requests scale with page size.

## Recovery: a real native concern, not the measured read bottleneck

Native Workbench writes pass synchronous `scheduler.flush()` at [mutation_outcomes.py:28–56](../../python/disco/recovery/mutation_outcomes.py#L28). Although recovery has a bounded delta feed, [workspace_state_snapshot.py:305–320](../../python/workspace_state_snapshot.py#L305) forces full pruned capture for changes to recipes, bindings, suggestions and every Workbench table, including a small draft decision. Incremental recipe-reference closure and changed-row after-images could avoid this full capture. Preserve exact root reachability, deletion, receipt replay, committed-but-backup-failed outcomes and crash recovery.

SQLite's [session extension](https://www.sqlite.org/sessionintro.html) provides a useful comparison: changesets retain enough old values to detect conflicts, while compact patchsets sacrifice some conflict detection. Our recovery design should retain the required evidence rather than optimize by dropping it. The existing native [recovery capture:348–406](../../python/disco/backup/recovery_generation.py#L348) already handles retention gaps and coherent locked capture; extend that proof rather than invent an unchecked delta log.

This is not an explanation for the measured 5.08-second fixture preparation: native recovery is enabled only with `dj.Schema` at [workspace_api.py:1914–1934](../../python/workspace_api.py#L1914), which this fixture lacks. It also cannot explain read-only selection latency. Conversely, the SQL double's [to_dicts:30–38](../../python/tests/test_workspace_curation.py#L30) deep-copies rows, and [transaction:75–76](../../python/tests/test_workspace_curation.py#L75) deep-copies all fixture tables on entry. Native MySQL fetch/deserialization/transactions differ. Do not optimize the double or assume native cost is either uniformly higher or lower.

## Falsifiable next experiments

These are proposed decision targets, not predictions or replacement benchmark thresholds.

| Experiment | Unchanged-fixture objective | Mechanism oracle and refusal gates |
| --- | --- | --- |
| Request-local projection + bootstrap/selection bundle | Replay and prepared return each below 2.0 s; select 100 below 1.25 s, with all existing cases passing and fresh preparation not regressing | Independently fresh closing reads; exact bodies/UUID order; one selection admission; fewer recipe reads/context builds; held baseline/recipe/draft/source changes reject; custom overrides retain fallback |
| Full attested prepared publication | On a separately owned native fixture of the same 1m/20k/100 shape, target warm page below 200 ms and selection/return below 500 ms after preparation; establish a native baseline first | Warm hits perform no full recipe decoding, full membership reconstruction or whole-project fingerprint scan; writer/reader race, same-UUID corruption, DDL, restore, missing triggers, reconnect, eviction and cancellation all reject or rebuild |
| Incremental pending/lineage + native recovery closure | After a 100-member change to a previously prepared 20k-member protocol, target native preparation below 2.5 s and recovery work proportional to changed rows plus newly referenced recipes | Exact overlap/removal/conflict outcomes, no inherited all-selection consent, unchanged old main curation, byte-identical durable replay, missing delta/full-rebuild behavior and crash/failure durability |

Keep the existing fixed thirteen-action benchmark and three ordinary samples. The native-only optimization must retain the current mutable SQL-double fallback; giving the benchmark an invented generation witness would invalidate the comparison. Separate cold preparation/build cost, warm reads, retained bytes, and native recovery costs. A supplemental size sweep may hold `K=60/100` while varying active membership to test the claimed asymptotic improvement, but does not replace the fixed workflow.

The next implementation should establish the reusable admission/projection boundary once and let multiple consumers use it. Additional local copy tricks or a cache keyed only by recipe UUID would leave both the scaling problem and the completeness-of-authority problem unresolved.
