# Disco release and CI audit

17 November 2026 · Public testing channel 0.2.15 · GitHub main `8179f329` · Published source `46501103`

**Give a small edit a trustworthy answer in under ten minutes. Spend the longer macOS checks on the failures a scientist would notice.** Three consecutive shipped candidates took 63–82 minutes. Ordinary PR regression already took a median of eight minutes. The largest opportunities are choosing the right tests, verifying the installed app earlier, and making a single noisy measurement cheap to investigate. The current written policy explicitly requires a million-row comparison after every application iteration. Adopting the recommendations would require changing that policy and its publication code together. ## Which failures should stop a release?

| User-visible failure | Current evidence and gap | Proposed blocking check |
|---|---|---|
| App hangs on launch, on Quit, or at the next open | Packaged smoke already creates a project, waits for readiness, quits within 45 seconds, checks process/registry cleanup and reopens the same project with a new session. Its helper launches a staged executable and requests Quit via a renderer bridge. Bootstrap tests intercept the native launch handoff. The PR desktop job uses Node on Ubuntu, and its macOS lifecycle job exercises MySQL and project transfer. | Launch via the installed macOS entry, open a populated project, request ordinary menu/OS Quit during startup and again from the ready state. Verify a bounded exit, owned service and lock release, and successful reopen with the same project ID and correct waveform. Run on lifecycle-impact PRs and every candidate. |
| Accepted edits or imports vanish, duplicate, or never finish during shutdown | Extended packaged cases for active H5 writes, real trace inspection, masks and export are conditional on an H5 path. The candidate workflow does not supply it. A successful extended run can omit these cases. A live GitHub feed check also precedes project/quit smoke. | Make required fixture availability an assertion. Use the existing donor-free H5 generator. Trigger Quit at a controlled accepted-write point. Verify the documented drain or recovery path, bounded exit and exactly-once durable result after reopen. Give the live feed a separate verdict so a timeout cannot hide the lifecycle result. |
| UI shows a plausible but wrong trace, count, edit or export | The repo already has a synthetic fixture with known epochs and responses, exact-result scale checks, and broader native cases. An app can launch cleanly and still display the wrong epoch. | In the short native path, check a known epoch/response pair and one persisted operation by identity. For the affected feature, click through selection, tags, undo, mask or export and compare the output with the fixture. Keep million-scale exactness for changes to queries or indexing. |
| An update breaks an existing installation, rollback or recovery | Native updater programs exercise meaningful install, recovery and rollback behavior, but manufacture the older version by relabeling a candidate clone. That misses compatibility defects unique to an actual older release. | For updater, schema, profile, runtime or packaging changes, upgrade the last supported public archive to the exact candidate, reopen a pre-existing project, and verify rollback/recovery as supported. Keep the digest and exact-source publication checks on every release. |

Disco has already fixed a pending backend startup continuing after explicit Quit. That change added a supervisor unit regression. It gives the proposed installed check a known failure to replay. Explicit Quit and update/replacement have different contracts. Explicit Quit has a 35-second internal deadline and can retain an interrupted operation for reconciliation at the next launch. A clean exit should release all owned services. In the interrupted case, check that no conflicting writer starts, the user sees recovery, and the next launch reconciles the recorded operation. Replacement requires clean preparation. The test should distinguish a valid recovery outcome from data loss or an indefinitely stuck window. Capture the last visible state, elapsed times, owned process tree, and operation record on failure. ## How to judge 124 ms

**The recorded 124 ms result did not merit rerunning the entire million suite.** The macOS trace job measured median time to the post-stroke observation at 98.5 ms baseline and 124.0 ms candidate. Its 25% cutoff was 123.125 ms. The exceedance was 0.875 ms, while whole-action time improved from 181.4 to 174.6 ms. An independent run on identical candidate source measured 116.3 ms baseline and 108.0 ms candidate. A separate frontend test flagged a stale retained-UI lifecycle review receipt. That check fingerprints the production dependency tree and links it to reviewed tests. It should still report separately from the runtime outcome. If 119.3 ms had been the baseline, 124 ms would already pass this comparator. [Initial job](https://github.com/maxwellsdm1867/Rieke-OS/actions/runs/43287795789/job/131426088439) · [Same-source repeat](https://github.com/maxwellsdm1867/Rieke-OS/actions/runs/43288389854/job/131428108730) · [Comparison formula](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/tools/benchmark_workflow.py#L367-L392)

PR #129 illustrates a different issue. On the first attempt the historical pin, immediate base and candidate measured 108.6, 349.9 and 334.2 ms to first waveform. The second measured 116.7, 166.6 and 166.5 ms. Both runs flagged historical drift. Neither established that the PR introduced the slowdown. The measured PR tree was GitHub's synthetic merge. The package used a separately qualified exact source. Repeating the whole workflow repeated the already-passing backend and native lanes. [Attempt one](https://github.com/maxwellsdm1867/Rieke-OS/actions/runs/43344377194/attempts/1) · [Attempt two](https://github.com/maxwellsdm1867/Rieke-OS/actions/runs/43344377194/attempts/2)

| Measurement | Proposed decision |
|---|---|
| Missing waveform, wrong epoch, dropped accepted write, hung quit, corrupt or mismatched bytes, missing required evidence | Block. Retain evidence and identify the failed workflow. |
| Small change in an internal paint or scheduling metric | Report the baseline, spread, candidate and user-visible endpoint. An isolated borderline result is advisory. No full rerun. |
| Material slowdown in an interaction a scientist feels | Compare candidate and immediate base on the same runner. Use a predeclared absolute and relative effect threshold informed by identical-source noise and UX. For a borderline primary metric, allow one additional paired measurement of that case and evaluate all samples together. A reproducible regression or a breached calibrated hard deadline blocks. |
| Candidate and immediate base both slower than historical pin | Track drift over releases. Assign an owner and investigate. A sustained breach of an explicit user-facing budget can stop release even when the latest PR is innocent. |

Start with launch to usable project, epoch click to first correct waveform, and ordinary Quit to actual exit. Keep separate cold/warm and small/large project conditions. Calibrate each runner and metric using repeated identical-source pairs plus a known regression. Current geometry compares both medians and maxima from three samples. Keep those maxima for diagnosis and gather enough independent runs before using tail latency as a gate. Faster CPython's A/A experiment provides a precedent for measuring the noise of the environment itself. [Geometry metrics](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/tools/benchmark_prepared_geometry.py#L125-L146) · [Faster CPython experiment](https://github.com/faster-cpython/ideas/issues/480) · [Google Benchmark repetitions](https://google.github.io/benchmark/user_guide.html#statistics-reporting-the-mean-median-and-standard-deviation--coefficient-of-variation-of-repeated-benchmarks)

## How the lesson changes Disco’s code

The existing Electron main process already owns the visible lifecycle. `QuitCoordinator` coalesces repeated Quit requests and gives cleanup a deadline. The supervisor independently verifies the identity and actual exit of owned services. Preserve those responsibilities. A statechart can describe their allowed behavior without introducing another object that claims to own the app state. [Electron composition](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/desktop/main.cjs#L145-L164) · [Quit coordinator](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/desktop/close/quit-coordinator.cjs) · [Supervisor](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/desktop/supervisor.cjs#L235-L285)

**One of the state transitions failed in current code.** We paused chooser authorization in the repository’s Electron composition fixture, issued ordinary Quit, then let authorization succeed or fail. Both outcomes replaced Closing with Recovery. A separate ordering let an already-admitted document finish loading and replace Closing with Current. A genuine recovery could also lose its original diagnosis. All four cases failed when replayed against the byte-identical main revision. The mocked exit callback still ran after cleanup. This establishes incorrect UI state during shutdown. The cause of any reported native hang requires the native check. [Original startup completion](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/desktop/main.cjs#L453-L477) · [Existing fixture](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/desktop/tests/main-startup-restoration.test.cjs)

The first patch uses the existing navigation generation, Quit intent and integrity state. Once a newer transition takes ownership, the old startup completion cannot publish a status or register a newly active view. Its cleanup still runs. Four deterministic replay tests exercise the orderings. They execute on the existing mapped PR test path. This moves a recurring correction into the interface the program already uses.

Two further changes follow from the same reasoning.

- **Make coverage explicit at the release boundary.** Add narrowly scoped native scenario IDs and required observations to the existing lifecycle ownership catalog. The planner names them and the harness reports each one as passed, failed or skipped with a reason. Accept a required scenario only if its expected observations exist. This prevents an absent H5 fixture from disappearing inside an otherwise successful suite. Keep the existing conservative paths for unknown changes. The current planner tests explicitly expect the quit coordinator and startup session to omit the richer UI suite. [Ownership catalog](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/docs/architecture/adopted-port-checks.json#L605-L656) · [Planner expectations](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/python/tests/test_desktop_release_plan.py#L157-L175)
- **Give the supervisor one way to establish clean stop.** Quit and replacement each check the stop acknowledgement and the child’s subsequent exit. Factor only the proof shared by both routes into the supervisor, tied to the same owned process and stop attempt. The callers still decide what a timeout means and what to do with drafts or recovery. Existing paired tests cover a rejected acknowledgement followed by exit zero, a signal and a nonzero exit. [Quit and drain](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/desktop/supervisor.cjs#L267-L352) · [Paired tests](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/desktop/tests/supervisor.test.cjs#L247-L273)

## Recommended rollout

1. **Prove the missing native check first.** Reuse the donor-free fixture. Click through the affected lifecycle in the native app before running baseline comparisons. Replay the historical startup/quit regression against a good and bad revision or an equivalent controlled failure. Make a missing H5 fixture, wrong waveform or surviving owned service fail visibly. Measure the full workflow time including packaging.
2. **Route by change and explain the selection.** Publish one PR summary listing the affected user workflows, selected tests, timing warnings, and the evidence needed to merge. Target a first actionable result within ten minutes at the 90th percentile on routine edits. Pure release-page work gets its focused tests. Trace/index changes get paired performance and scientific correctness. Lifecycle changes get the native transition test. Shared runtime, dependency, CI-policy and unclassified changes take the broader route. Run the old and proposed selectors side by side before switching.
3. **Make the performance policy and publisher agree.** Today artifacts include the attempt number, the aggregator reads that attempt, and the publisher uses the latest workflow run for the source and recomputes its verdict. A YAML-only change will leave publication blocked. Accept selected immutable lane receipts only when source tree, base, harness, fixture, runtime, policy, platform and candidate digest where applicable all match. Bind them to explicit trusted runs, retain superseding failures, distinguish diagnostic runs, and reject missing or incompatible evidence. Rehearse failed-job-only retries and a PR merge SHA versus an exact release SHA. [Aggregate](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/.github/workflows/everyday-million.yml#L327-L354) · [Publisher](https://github.com/maxwellsdm1867/Rieke-OS/blob/8179f329/tools/desktop_source_ci.py#L167-L236)
4. **Make release qualification one intentional operation.** On a release request, build one archive, start the necessary source checks in parallel, select native suites relative to the last published release, and expose one readiness summary with the exact candidate. Prefer releasing an integrated main commit so the merge, packaging and publication evidence can identify the same revision. Preserve the deliberate publish action. With the recorded build and smoke alone, a routine candidate would still take roughly 41 minutes before publication. That is an arithmetic estimate. Reaching a materially shorter routine release also requires reducing the 34-minute build or reusing an already verified exact artifact. On high-risk releases, parallelize the two updater programs and test an authentic previous package.
5. **Give deferred failures an owner.** Run broad historical performance, long lifecycle interleavings and randomized UI sequences on a scheduled main build. Keep an on-demand full qualification. Track PR feedback p50/p90, request-to-publish time, macOS runner minutes, repeated green jobs, actionable timing failures, and escaped startup, shutdown or data-integrity defects. During rollout, compare the proposed verdict against the current one on each release and investigate every disagreement before retiring a gate.
